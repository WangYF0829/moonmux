# moonmux 设计说明

## 一、要解决的问题

MoonBit 生态在音频方向存在一个**单边断层**：

| 环节 | 生态现状 |
|---|---|
| 读容器（demux） | `isobmff`（MP4 解析）、`moontsinspect`（TS 检查） |
| 解码 | `moonopus`、`moonvorbis`、`mp3.mbt`、`moon-wav`、`moonwavkit` |
| 播放 | `moon_rodio`、`moon_cpal` |
| **写容器（mux）** | **没有** |
| **转码管线** | **没有** |

也就是说：音频数据能解码、能播放，但**存不回文件**。这条链的出口是堵死的。

moonmux 补的是出口 —— 容器写入与转码管线。

## 二、技术选型

**容器格式选 Ogg 而非 MP4。** 理由：

1. Ogg 的页结构简单（固定头 + 段表），一个页的解析器可以在数百行内写透；ISOBMFF 的 box 树、track 交织、moov/mdat 布局复杂度高一个量级。
2. 生态里已有 `moonopus` 与 `moonvorbis` 两个纯 MoonBit 的 Ogg 音频解码器 —— 补上封装层即可闭环，形成「解码 → 封装」的完整链路。
3. 相比 MP4，Ogg 方向的实现者更少，空白更彻底。

**不依赖任何三方包。** 容器格式的正确性必须能被独立验证，不该被解码器的实现缺陷掩盖。写字节用的 `Buffer` 来自 prelude，无需额外引入。

## 三、模块结构

```
moonmux/
├── ogg/         Ogg 容器层（核心）
│   ├── crc.mbt      CRC-32，RFC 3533 参数
│   ├── page.mbt     页结构：解析与序列化
│   ├── packet.mbt   段 → 包重组、包 → 段表切分
│   ├── mux.mbt      逻辑流分组、多流交织
│   └── stream.mbt   字节流 ↔ 页序列
├── wav/         WAV 容器层
│   └── wav.mbt      RIFF/PCM 解析与编码
├── pipeline/    转码管线（唯一引入三方解码器的包）
│   └── pipeline.mbt 编码格式识别 + Opus / Vorbis → WAV
├── cli/         命令行解析（纯逻辑，无副作用）
│   └── cli.mbt      argv → Command 值
└── cmd/main/    命令行入口（仅做 I/O）
```

`pipeline/` 之外**不引入任何三方包**。`ogg/` 与 `wav/` 的 import 块至今是空的。

## 四、关键设计决策

### 1. CRC 用「两次构造」而非「先写占位再回填」

Ogg 的 CRC 计算范围是**除捕获模式外的整页字节**，且计算时 CRC 字段自身必须置零。直觉做法是先写一个占位的 0，算完再回填 —— 但 MoonBit 的 `Bytes` 是不可变的，没有索引赋值。

因此改为：把「写入页体」抽成一个接受 CRC 参数的函数，第一次传 0 用于计算校验值，第二次传真实值构造最终字节。代价是页体写两遍，收益是不需要任何可变字节缓冲，也不需要危险的回填操作。

### 2. `cli/` 与 `cmd/main/` 分离

参数解析最容易出「答非所问」的错误 —— 拼错的子命令被当作文件名、缺参数时报出无关提示、多余的参数被静默忽略。这类 bug 只有在真敲命令时才会暴露，因为解析逻辑通常长在不做测试的入口函数里。

把 argv → Command 的映射抽成无副作用的纯函数后，每条分支都能被断言钉住（见 `cli_wbtest.mbt` 的 7 个测试），入口层退化为纯粹的 I/O。

### 3. 截断的流宁可少给包，不给半截数据

`reassemble` 在遇到「段表以 255 结尾但后面没有更多的页」时，会丢弃这段不完整的数据而不产生包。容器解析的常见错误是把不完整数据当作合法结果交出去，让问题在下游以更难定位的形式爆发。

同一条不变量还要求：段表各项之和必须恰好等于该页负载长度。两者不符说明这一页本身已损坏，此时整条流上尚未成形的数据一并丢弃，而不是继续按错位的偏移去读。

### 4. 包按逻辑流分流，而不是共用一个累加器

Ogg 允许同一字节流中交织多条逻辑流（Ogg Skeleton、音视频复用）。最初的重组实现用**单个**累加器按页顺序吞段，于是流的边界被打通：流 1 的 255 字节会和流 2 的 1 字节粘成同一个包，并且被标成流 2 的 `serial` —— 数据错了，元信息也错了。

单流文件（生态里绝大多数音频，也是本项目的测试样本）发现不了这个问题。现在每条逻辑流各持一个独立的累加器，按 `serial` 分流。

### 5. 页切分属于容器层，不该推给调用方

RFC 3533 规定单页最多 255 个段，即单页负载上限 255×255 = 65025 字节。页头的**段数字段只有一个字节** —— 不做拆分而直接把超出的段数写进去，长度会被静默截断，页结构随之崩坏，而调用方拿到的是一份「看起来写入成功」的字节流。这类错误不会抛异常，只会在很久以后以「文件打不开」的形式出现。

因此把「包序列 → 页序列」的切分固化成 `paginate`：它负责按 255 段一批拆页、给续页打 continued 标志、只在包结束的那一页写粒度位置（其余写 -1），并在首页 / 末页打 BOS / EOS。命令行入口直接调用它，而不是自己拼页。

### 6. 三方依赖只许出现在 `pipeline/`

「不依赖三方包」这条原则的真正理由不是洁癖，而是**可验证性**：容器格式的正确性必须能被独立验证，不该被解码器的实现缺陷掩盖。如果 `ogg/` 依赖了某个解码器，那么 CRC 算错时根本说不清是谁的错。

但转码又不可能自己写解码器 —— 那不是本项目的方向。于是把依赖隔离成一个包：`pipeline/` 上游用本项目的 `ogg/` 拆包并识别编码格式，解码交给生态里已有的纯 MoonBit 解码器（`LL728/moonopus`、`LL728/moonvorbis`，均无 FFI），下游再用本项目的 `wav/` 编码落盘。容器层的进出两端都在自己手里，中间那段是别人的；一旦解码出问题，责任在哪一侧一眼可见。

编码格式的识别也放在这一层，并且用**首个逻辑包的头部标记**判断（Opus 是 `OpusHead`，Vorbis 是 `0x01` + `vorbis`），而不是看文件扩展名 —— 扩展名可以随便改，而规范保证标识包必然是流的第一个包。

### 7. 多逻辑流交织：BOS 页置顶，数据页按粒度归并

一个物理流（文件）可以承载多条逻辑流，交织时要守 RFC 3533 的两条约束：

1. **所有 BOS 页排在最前面**。解码器在解任何数据之前，要先读到每条流的头部包（OpusHead、Vorbis 识别头）才能决定怎么解。因此既不能「流 1 全部写完再写流 2」，也不能把 BOS 页混进数据页中间。
2. **此后按粒度位置升序归并**。粒度位置就是时间：播放器顺序往下读，播到第 N 秒时手上必须已经拿到所有流第 N 秒前后的数据。某条流若一股脑写在前面，播放器要么缓冲区撑爆，要么读到的是过期数据。

粒度位置为 -1 的页（本页没有包结束）自身没有时间，归并时沿用该流上一条已知的粒度 —— 它本来就是上一页的延续。

分组顺序取**流在文件中首次出现的顺序**，不按流号排序：流号是随机分配的，大小与文件里的先后顺序无关（Ogg Skeleton 的骨架流必须先出，但它的流号未必最小）。

### 8. 目录布局表达流结构，且不允许两种布局混用

`demux` 按逻辑流分组输出（`s1/` 、`s2/`……），`mux` 反过来按目录布局还原：有子目录时每个子目录一条逻辑流，没有时整目录一条。分组是必要的 —— 包文件本身不带流号，若把所有流平铺进同一个目录，重新封装时就无法再把它们分开，多逻辑流文件会不可逆地退化成单流。

两种布局混在一起时**报错**而不是挑一种：无论选哪一种都会漏掉另一半数据，而这种遗漏在产物里看不出来 —— 文件照样能解析，只是少了一条流。

封装时流号重新编号为 1、2、3……，不沿用原文件的流号：包文件里不带流号，目录布局只表达了「有几条流、各自有哪些包」。原流号在 `demux` 的输出里给出。

### 9. 包文件名序号补零到固定六位

包文件按名字典序读出，因此序号必须补零到**固定宽度**。宽度若按实际包数收缩，位数就会不一致：`"1000"` 会插在 `"100"` 与 `"101"` 之间（第三位 `'0' < '1'`），包数超过 999 时静默乱序。三分钟的音频轻轻松松就有九千个包（20 ms 一帧），所以直接留够六位。

## 六、测试策略

测试走 `wasm-gc` 后端，不依赖 C 编译器，便于在任意机器上复现。当前 49 个测试全部通过。

覆盖的不变量：

- **CRC 参数正确性**：用权威校验值 `0x89A1897F` 钉死。该值经独立实现交叉验证，并通过 cksum 对照值 `0x765E7680` 反推确认。参数取错会导致生成的 Ogg 被所有解码器静默拒绝。
- **CRC 覆盖范围**：校验值必须覆盖整页（含捕获模式 `OggS`），用向量 `0x9663CDB4` 钉死 —— 排除捕获模式的错误实现会得到 `0x55CD9637`，且所有往返测试照常通过。
- **独立复核路径**：`page_crc_ok` 对已解析的页重算 CRC，负载改动一个字节即报否 —— 这是 `verify` 命令的判据。
- **往返一致性**：页的序列化与解析互逆；重新序列化逐字节幂等。
- **边界条件**：长度恰为 255 的包的段表必须是 `[255, 0]`；空输入 CRC 为 0。
- **跨页包**：256 字节的包跨两页时能被重组成一个包，而不是两个碎片。
- **超长包跨页**：65026 字节的包经 `paginate` 拆成两页，每页段数不超过 255，序列化—解析—重组后数据一字不差。
- **多流分流**：交织的两条逻辑流各得其所，流 2 的 1 字节包不被流 1 的数据污染。
- **多流交织**：所有 BOS 页排在数据页之前，且条数与逻辑流数相等；数据页按粒度升序归并（不是把某条流一口气写完）；每条流的页序号各自从 0 编号。
- **多流往返**：两条流交织写出后经序列化—解析—重组—分组，各流包内容与条数逐字节不变（含一条 70000 字节的超长包）。
- **重复流号被拒**：两条流用同一个 `serial` 时返回 Err —— 相同流号会让 `reassemble` 把包粘在一起，静默接受只会把错误推迟到解码阶段。
- **损坏页不崩溃**：段表声称的长度超出实际负载时丢弃而非越界读。
- **WAV 输入校验**：RIFF 声明长度超出文件、格式字段为 0 的输入被拒绝。
- **32 位长度字段防溢出**：块长度读成 Int64，高位被置 1 的长度（如 0x80000000）按超界拒绝，而不是被 32 位有符号读法变成负数绕过检查。
- **调用方偏移校验**：`is_page_start` / `Page::parse` 对负偏移安全拒绝，不索引到负数位置。
- **CLI 分支**：每条参数错误路径都有断言，包括**多给参数必须报错**而非静默忽略。

- **转码管线**：识别编码用的是**包内容**而非扩展名；无法识别的流如实返回 Err，而不是写出一个安静的空 WAV。

`pipeline/` 的测试只覆盖管线自己的职责（识别、分派、报错），不验收解码结果 —— 把外部解码器的行为钉进自己的测试，等于把别人的改动变成自己测试的红绿灯。真实解码的验收走命令行与 `testdata/`。

除单元测试外，还有一层外部验证：解析真实的 Opus / Vorbis 文件，逐页重算 CRC 与标准编码器写入的值比对；把真实文件的全部包拆出再重新封装，产物的逐页 CRC 与负载字节数与原始文件一致；转码产物用 Python 的 `wave` 模块独立解析，并检查 RMS 与非零样本比例，确认解出的是真实音频而不是一片静音。

多逻辑流另有两轮验证：把 Opus 样本（303 包）与 Vorbis 样本（48 包）的包合成两条流交织封装，产物经独立脚本复核页结构（逐页 CRC、段数与负载不超限、BOS 页置顶、每流页序号连续、每流都有 EOS）；再拆回两条流，与原始包逐字节比对一致。1200 个包的目录另做一轮封装—拆包往返，确认序号超过 999 后顺序不乱。
